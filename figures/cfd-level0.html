Discussion

The Context Flow Diagram (Level 0) represents Knowing Eye as a single process, P0, and identifies every external entity that exchanges data with the system. Internal sub-processes - authentication, exam delivery, AI-based behavior analysis, and reporting - are intentionally not shown here; those are expanded in the Level 1 Data Flow Diagram. What this diagram establishes is the system's boundary: what comes in, what goes out, and who or what the platform depends on.

Four external entities interact with the platform. The Examiner/Admin creates exam definitions, manages sections and user accounts, and queries reports; in return, the system provides dashboards, behavior alerts, analytics reports, and CSV exports. The Examinee supplies login credentials, OTP verification codes, exam answers, and face-enrollment frames, and receives exam content, timers, scores, and feedback. The Webcam Device, accessed through the browser's media API, streams live video frames used for real-time facial and postural monitoring, while the system issues capture start/stop control back to it. Finally, an external Email/OTP Delivery Service sends one-time passcodes and account notifications on the system's behalf and reports delivery status back to Knowing Eye.

Neither a database nor a web/API server is drawn as a separate box, and that is deliberate rather than an omission. At Level 0, a Context Diagram treats the entire system as one black-box process; only entities that sit outside that boundary are shown. Knowing Eye's own database (PostgreSQL in production, SQLite in development, per backend/core/config/settings) is provisioned and owned by the system itself, so by DFD convention it is a data store that belongs inside the Level 1 diagram, not an external entity here - the same is true of the Django API server, which is what "P0" represents at this level, not something separate from it. The Email/OTP Delivery Service earns its place on this diagram precisely because it fails that test: OTP mail is actually dispatched through a Supabase Edge Function running outside the application's own codebase and hosting (see core/utils/supabase_email_backend.py), which makes it a genuine external dependency rather than an internal component wearing an external label.
