Access Control (RBAC + PBAC)

Per the Capstone Defense Revision Directive, Area 01 ("Authentication, Roles & Access Control"): a single administrator account is a bottleneck and a single point of failure. Access is enforced in three tiers (backend/core/security/), mirroring the LCC OSAS System pattern: role guard (is this broadly this kind of user?), module access (can this user see this feature area?), and action permission (can this user perform this specific mutating operation?). An explicit per-user deny always overrides a role default; an explicit grant can extend it — so an admin can delegate a narrower slice of access without changing anyone's role.

Program HeadLevel 1exams.create, exams.update, exams.approve, behavior.resolve, reports.export, sessions.gradeReviews and approves submitted exams before they can publish

Full registry in backend/core/security/modules.py (module visibility) and backend/core/security/permissions_registry.py (action grants).

Exam approval chain

Directly answers Area 01's "Administrator responsibilities" item: stop making the administrator responsible for creating every exam. Teachers, Guidance Staff, and Program Heads create and submit exams; a Program Head (or Admin) reviews, approves, or rejects them. Only an approved exam may be published by a non-admin creator — an admin retains the same bypass it holds everywhere else in the system, so this adds a review gate without introducing a second point of failure.

1. Draft

Creator builds the exam. approval_status = not_submitted.

2. Submit

Creator submits once publish-readiness passes (≥1 question, valid answer keys). approval_status = pending; logged to exams_approval_event.

3. Review

Program Head/Admin approves or rejects (with a note). Rejection returns the exam to the creator, who can revise and resubmit.

4. Publish

approval_status = approved unlocks POST /api/exams/{id}/publish/ for the creator; exam status moves draft → active.

Registration & OTP verification

Answers Area 01's "Registration & verification" item. Registration collects only essential fields — the profile photo is optional at signup and can be added later from the profile page, rather than blocking account creation. Password confirmation is required. Immediately after account creation, a 6-digit OTP is emailed; the code is stored hashed (never in plaintext), expires after 10 minutes, allows 5 incorrect attempts before requiring a resend, and is rate-limited to one send per 60 seconds. A "Verify your email" banner in the signed-in workspace (dismissible per session, not a hard gate) makes the pending step visually clear without blocking use of the app.

Exam Discovery, Scheduling & Lifecycle Locks

Directive Area 03 ("Exam Management & LMS Behavior") - see the LMS Benchmarking matrix for how each item below was checked against Google Forms, Jotform, and Moodle before being built.

Categories, multi-department assignment, and search/filter/sort

ExamCategory is a new classification axis seeded with the three Guidance content types the Directive names - Psychological, Mental / Abstract Reasoning, Behavioral / Character - deliberately not academic subjects. Exam.department stays a single FK (it generates the exam code and can't change after creation), and a new Exam.departments M2M holds every department an exam should be discoverable from; creating an exam defaults departments to just the home department, so nothing loses visibility, and a shared/general-ed exam can add more. This directly answers Area 03's "reconsider whether department should be a primary exam attribute" - it demotes department from the exam's only classification axis to one of three (department, category, and now a proper M2M) without removing the code-generation behavior that already depends on it.

The exam list endpoint's SearchFilter/OrderingFilter/filterset_fields (status, category, department, approval_status - already present before this sprint) is now paired with a reusable <FilterBar> component (search + status/category chips + a sort dropdown) on the examiner dashboard, replacing an inline search box and status-only chip row that filtered nothing but status client-side.

Derived schedule state

A published exam now reports one of four states - Upcoming, Active, Closed, Expired - computed from status and the existing available_from/available_until window (services.exam_schedule_state), never stored: Draft exams report no state (the window isn't meaningful yet), Archived always reports Closed regardless of the window, and an Active exam reports Upcoming/Active/Expired by comparing "now" to the window. The window itself was already enforced server-side before this sprint (assert_exam_available_for_user blocks session start once the deadline passes) - this sprint's work was making that enforcement visible as the four named states, not adding the enforcement itself.

Question editing locked during an active session

assert_exam_editable already blocked edits on any non-draft exam; it now additionally raises the moment any examinee has a setup or in_progress ExamSession against that exam (exam_has_active_session), with a message naming the actual reason rather than just "not a draft." This is the literal mechanism the Directive names - "students may already be answering" - checked against live session state instead of only inferred from the exam's publish status.

Image-based answer choices

Question.options moved from a flat list of strings to a list of {"text": str, "image": str | null} objects (migration 0013 backfills every existing row losslessly). A new POST /exams/{id}/questions/{id}/option-image/ endpoint uploads one image and returns its URL for the client to attach to an option - for the abstract/psychological items the Directive calls out by name, where the answer choice is a shape or image rather than text. Existing plain-string API payloads are still accepted and normalized (option_text() in serializers.py), so nothing that posted the old shape breaks.

Bulk import: media references

The CSV/XLSX template gained an optional option_images column, pipe-delimited and positionally aligned with options. The importer validates the segment count matches options and that every non-empty reference looks like a usable URL (http(s):// or a same-origin /media/ path) rather than a typo'd filename - the "validate ... media references" line item from Area 03's bulk-import requirement.

Essay results held for grading

ExamSession.submit_session already moved a session with any ungraded flagged response (essay, or a short answer that didn't auto-match) into PENDING_REVIEW. What was missing was the other half: the session's score fields were still serialized to the examinee even while pending review, showing an artificially low score (ungraded essays score 0 until graded). total_score/percentage_score/passed are now withheld from the examinee (graders still see them, for context while grading) until every flagged response is graded; finalize_grading_if_complete then recomputes the score, flips the session to Completed, and emails the examinee that results are ready - so "hold essay results" and "email notification on release" are the same mechanism, not two separate features bolted together.

AI / Computer Vision

Production pipeline: backend/ai/knowing_eye/, integrated through backend/ai/adapter.py. Pre-trained benchmark accuracies below are from published model evaluations; project-specific UAT metrics are tracked in Part D.

MediaPipe Face & Pose

In project: face_detector.py and pose_detector.py extract 468 face landmarks, head yaw/pitch, and body keypoints for gaze and posture scoring.
Accuracy: Face detection ~98% precision on frontal faces; pose landmark PCK@0.2 ~95% on visible joints (Google benchmarks).

ArcFace / InsightFace (buffalo_l)

In project: arcface_backend.py produces 512-D embeddings; enrolled at exam start and verified each frame via cosine distance (identity_match_threshold: 0.42 in pipeline.yaml).
Accuracy: LFW 99.77%, CFP-FP 98.56%, AgeDB-30 98.18% (InsightFace model zoo).

OpenCV + NumPy

In project: preprocessing/frame.py handles BGR conversion, resize (≤640 px), denoise, and YCbCr histogram equalization before inference.

Threshold-based behavior classifier

In project: behavior/scoring.py and behavior/temporal.py map detections to 0–100% compliance metrics, rule-based event flags, and sliding-window suspicious-pattern alerts.

UI Readability & Contrast Audit

Directive Area 02 ("Readability & contrast"): the panel cited poor contrast, an overly dark default theme, and "eliminate gray-on-gray combinations." Two root causes were found and fixed, and every design-token pair was measured against WCAG 2.1 (4.5:1 for body text, 3:1 for large text and UI-component boundaries like input borders) rather than adjusted by eye.

Root cause 1 — the app defaulted to dark for every first-time visitor

core/providers/theme-provider.tsx set defaultTheme="system", and the toggle button in shared/components/common/theme-toggle.tsx independently manipulated <html>'s class list with its own useState("dark") default — bypassing the theme provider entirely and defaulting anyone without a saved preference to dark, regardless of system preference. Fixed: the toggle now reads/writes theme exclusively through next-themes' useTheme(), and the provider defaults to light.

Root cause 2 — input and button borders were measured, not eyeballed, and found near-invisible

Decorative-only borders (card outlines, table dividers, section rules) were deliberately not pushed to the 3:1 UI-component threshold — WCAG 1.4.11 scopes that requirement to boundaries needed to identify a component, and these carry redundant cues (shadow, background shift); forcing every card outline to 3:1 would have been a much larger, unrequested visual change for no accessibility gain. All values computed via the WCAG relative-luminance formula against the actual rendered/composited color, not the raw token in isolation.

Every ratio above is asserted, not just written down: frontend/src/styles/theme-contrast.test.ts reimplements the WCAG relative-luminance formula and fails the build if a future token edit regresses a pair below its threshold. Disabled controls (.icon-btn:disabled's 0.45 opacity, the shared Button/Input disabled:opacity-50 utility) are deliberately excluded from that test rather than silently ignored — WCAG 2.1 SC 1.4.3 and 1.4.11 both exempt inactive UI components from contrast requirements, so opacity-dimming is the correct treatment, not a gap.

Directive Area 04 ("Define every CV parameter", P0) - the panel's most technical line of questioning: "are your threshold values based on research, or did the team just decide them?" Every value below is the literal, live production value from backend/ai/config/pipeline.yaml - the same file is annotated with the same citations inline (search for "Directive Area 04" in that file). Threshold justification

Directive Area 04 ("Threshold justification", P0) asks four things explicitly: define "anomaly" precisely per parameter, base thresholds on cited research rather than internal judgment, make Normal → Suspicious → Anomalous explicit tiers rather than a binary flag, and factor in duration/frequency rather than single-frame events.

Anomaly, precisely: for every parameter above, an anomaly is not "the metric crossed the line once" - it is the metric remaining on the wrong side of its threshold for longer than that parameter's grace period (no_face_grace_seconds, leaving_seat_grace_seconds), or recurring often enough within the 60-second/3-flag window to count as a pattern rather than a glance. This directly answers the Directive's fourth requirement - no_face_grace_seconds: 2.0 and the suspicious_pattern window were built for exactly this reason, and are the citable answer to "why don't you flag every blink."

ThresholdValueBasis
identity_match_threshold0.42 cosine distance (≈0.58 similarity)InsightFace's own model-selection guide gives a worked example verification threshold of 0.40 cosine similarity for buffalo_l-family embeddings (InsightFace, "Choosing a Face Recognition Model"). Knowing Eye's 0.42-distance / 0.58-similarity bar is stricter than that reference example - a deliberate choice, since a false accept (letting an impersonator through) is a worse failure mode for exam integrity than a false reject (prompting a legitimate examinee to re-center in frame).
gaze_yaw_threshold_deg / gaze_pitch_threshold_deg40° / 35°Published proctoring-CV literature confirms gaze/head-pose deviation as the standard cheating-detection signal but does not converge on one universal degree threshold - published systems tune it per camera geometry and typically pair it with a duration requirement rather than a single angle (Yassine et al., "AI-assisted Gaze Detection for Proctoring Online Exams"). Knowing Eye follows that duration-pairing practice: 40°/35° alone does not flag anything - it must also persist across the temporal window (see Anomaly, above) before it becomes an event.

Escalation tiers: Normal → Warning → Suspicious → Critical → Action

Per-event Alert.severity (low/medium/high) already existed before this sprint, but nothing counted repeated or combined signals into a session-level escalation state - each alert was evaluated alone. backend/features/behavior/escalation.py adds that layer without replacing per-event severity:

Normal

No unresolved flags in the rolling window. No action.

Warning

A single low/medium-weight signal. Logged only - not surfaced to the proctor as an alert.

Suspicious

Weighted signal total crosses the suspicious-pattern bar, or the existing min_flags repetition rule fires. Raises a proctor-visible Alert.

Critical

Weighted total crosses a second, higher bar, or an identity_mismatch occurs at all (single-occurrence critical, per its 0.95 weight). Raises a high-severity Alert explicitly flagged recommend intervention.

Action

Deliberately kept manual. Critical surfaces a recommendation on the live monitoring dashboard; a proctor still clicks the existing sessions.terminate action to end a session. Auto-terminating a student's exam from a CV heuristic alone - with no human in the loop - is a consequential, hard-to-reverse action against a real person, and false positives are possible by design (that's what "suspicious" vs "certain" means). The Directive asks the ladder to define what happens at each tier, not that every tier act autonomously.

Combined-signal weighting reuses pipeline.yaml's existing metric_weights (face/gaze/posture/identity) rather than inventing a second weighting scheme, per the Directive's instruction to weight combined signals higher than one isolated signal. Covered by backend/features/behavior/tests/test_escalation.py with synthetic event streams - deterministic, no webcam or ML dependency required, so it runs in every CI pass.

Algorithm Comparison

Directive Area 04 ("Algorithm comparison", P0): benchmark the current stack against at least one alternative each, on accuracy, speed, and resource cost, and justify the pick. Correction alongside this comparison: four documentation pages previously described the pipeline as using MediaPipe, YOLOv8, and ArcFace. backend/requirements-cv.txt and every import in backend/ai/knowing_eye/ were checked directly - there is no ultralytics dependency and no YOLO code anywhere in this repository. That claim was inaccurate and has been corrected in Part B, Part C, Part D, and Part E of this chapter. Knowing Eye has never run YOLO; the two questions below are the honest reason why.

Dataset Methodology

Directive Area 04 ("Dataset methodology", P0) asks for data source, collection method, sample size, cleaning/annotation process, and a stated, justified train/test split. The honest answer, checked directly against the repository: no training data exists yet. backend/ai/training/ and backend/ai/training/data/ (the paths pipeline.yaml's paths.training_data_dir points at) are present but empty, and there is no training script anywhere in backend/ai/.

This is not an oversight to apologize for - it follows directly from the algorithm choices above. MediaPipe and ArcFace/InsightFace are used as frozen, pre-trained models; Knowing Eye does not fine-tune or train either one. The "dataset" the Directive is really asking about is therefore not a training corpus but a held-out evaluation set used to measure the pipeline's classification performance against the thresholds above - and that evaluation methodology is fully specified in Part D, AI Behavioral Classification Evaluation, correctly labeled there as planned methodology to be executed during the Capstone 2 deployment window, not results that already exist. Reporting fabricated accuracy numbers ahead of that data collection would fail the exact rigor the panel is asking for.

Split ratio, stated and justified in advance of collection: 70/15/15 (train/validation/test) nominally follows convention, but because no model here is trained, the "train" partition is reserved for future fine-tuning work and unused by the current evaluation; the operative split for Part D's held-out classification benchmark is effectively validation vs. test, drawn from mock-examination sessions run during the deployment window described in Part E.

Snapshot Monitoring & Proctor Dashboard

Directive Area 04 ("Snapshot monitoring & proctor dashboard", P1). Per the Directive's own "what the panel already liked" note, snapshot-over-continuous-video was accepted as a reasonable tradeoff at Capstone 1 - this section documents that decision precisely rather than re-arguing it.

  • Cadence: target_fps: 5 in pipeline.yaml - periodic snapshots over the existing WebSocket channel (/ws/monitoring/{session_id}/), not a continuous video stream.
  • Why: five analyzed frames per second is enough to catch sustained behavior (the shortest grace period, no_face_grace_seconds, is 2 seconds = ~10 frames of headroom) without the bandwidth or server CPU cost of encoding/transmitting/decoding full video for every concurrent examinee - the per-examinee cost that server capacity planning (Sprint 5, Directive Area 04 "Capacity & hardware") will load-test against.
  • Trigger: continuous while status = in_progress; frames stop being analyzed the moment a session leaves that state (submit, terminate, or expiry).
  • Retention policy: raw frames are not stored by default (KE_STORE_FRAMES=False) - only the derived metrics and behavior events persist (BehaviorLog, Alert). This is a deliberate privacy choice given many examinees are minors: the system needs to know that a face-absence or identity-mismatch pattern occurred, not to retain a video record of the examinee's face indefinitely.
  • Proctor locator: ExamAssignment.seat_label (optional, settable via the candidate roster CSV import alongside extra_time_minutes) surfaces on the live-session card and the session CSV/PDF export, so a flagged examinee is findable physically - "Seat Room 3 - 12," not just a name in a list row.
  • Camera-preview widget: the examinee-facing dock (proctoring-dock.tsx) already uses position: fixed pinned to a viewport corner - verified, not rebuilt, since it does not drift on scroll by construction.

Browser-Side Deterrents

Directive Area 04 ("Browser-side deterrents", P2). Right-click, text selection, and copy/cut are disabled on the exam-taking chrome (question text, navigator) - but explicitly not inside an answer <input>/<textarea>, since a student must still be able to select, cut, and rewrite their own response (focus-shell.tsx, isEditableTarget guard). Tab-switch detection was already wired end-to-end at the logging layer (ExamSessionViewSet.log_event, SessionLog.EventType.TAB_HIDDEN) but nothing compared the count against Exam.max_tab_switches - the exam-taking hook now counts hidden-tab events client-side and surfaces a warning banner once the configured limit is exceeded, in addition to the existing raw event log.

These are deterrents, not security controls, and are documented as such per the Directive's explicit instruction not to overclaim. A student using a second physical device, a phone, or printed notes is not stopped by any of the above - disabling the browser context menu does not prevent screenshotting with an OS tool, and tab-switch detection only observes the tab hosting the exam, not what's visible on a second monitor. The identity/gaze/posture CV pipeline and human proctor review remain the actual integrity controls; these browser affordances raise the effort required for the most casual attempts (copy-pasting exam text, alt-tabbing to a browser search) and nothing stronger is claimed for them here.

Load testing

Harness: scripts/load/ (Locust, driving both the REST health endpoint and the WebSocket snapshot channel at the real ~1fps frontend cadence). Full methodology and how to re-run it: scripts/load/README.md.

What was actually run: the Directive's 5→10→20→30→50→100 concurrency ladder was not completed at target scale on this development machine, and that is reported honestly rather than papered over. The development laptop available for this sprint had well under 1GB of free system RAM throughout testing (0.19-0.94GB, fluctuating for reasons unrelated to this test - other work already running on a shared machine), which is not a safe or representative environment to push to 100 simulated concurrent ML-inference connections. Answering the Directive's question

"Can it handle ~30 examinees in a room, and ~100 overall?" Honest answer: not established empirically at that scale yet. What is established: the harness that measures it is built, debugged (three real bugs were found and fixed while validating it - see scripts/load/README.md), and ready to run the full ladder in one command against hardware with confirmed free CPU/RAM headroom - a dedicated test VM or server, not a shared development laptop mid other work. Reporting "yes, 100" without having run that test would be exactly the kind of unresearched claim this whole sprint exists to eliminate. The n=3 result plus the memory-pressure finding are real, defensible data; the 30/100 target-scale numbers are the next, mechanically straightforward step once suitable hardware is available.

CV Pipeline Stages

1. Data Collection

Browser getUserMedia() captures webcam video; canvas encodes JPEG/base64 at ~1 FPS. Transport: WebSocket /ws/monitoring/{session_id}/ (REST /api/monitoring/frame/ fallback).

2. Pre-processing

Base64 → BGR; resize to ≤640px; optional denoise; YCbCr histogram equalization. Config: backend/ai/config/pipeline.yaml.

3. Feature Extraction

MediaPipe (468 face landmarks, head yaw/pitch, posture ratios) and ArcFace identity embedding.

4. Classification & Scoring

Threshold-based 0–100% metrics, rule-based event flags, sliding-window temporal patterns, and weighted aggregation into overall_compliance_pct.
