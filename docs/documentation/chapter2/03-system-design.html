System Design

Database structure, data dictionary, and the technologies, models, and algorithms used for data collection through classification in the Knowing Eye platform.

Entity-Relationship Diagram (ERD)

Knowing Eye uses a relational SQL database (SQLite in development, PostgreSQL in production). The ERD reflects Django models under backend/features/.

JSON Schema Diagram

Omitted. Knowing Eye persists structured data in SQL tables via the Django ORM. JSON fields (options, metadata, embedding) are embedded columns validated at the application layer, not standalone JSON document stores. Per capstone guidelines, JSON Schema diagrams are omitted for SQL-based databases.

The API response contract for frame analysis (used by the frontend and WebSocket) follows this structure:

{
  "metrics": { "face_presence_pct", "gaze_focus_pct", "posture_compliance_pct",
               "identity_match_pct", "overall_compliance_pct" },
  "events": [{ "event_type", "score_pct", "confidence_pct", "metadata" }],
  "alerts": [{ "type", "severity", "message", "metric_pct" }]
}

Access Control (RBAC + PBAC)

Per the Capstone Defense Revision Directive, Area 01 ("Authentication, Roles & Access Control"): a single administrator account is a bottleneck and a single point of failure. Access is enforced in three tiers (backend/core/security/), mirroring the LCC OSAS System pattern: role guard (is this broadly this kind of user?), module access (can this user see this feature area?), and action permission (can this user perform this specific mutating operation?). An explicit per-user deny always overrides a role default; an explicit grant can extend it — so an admin can delegate a narrower slice of access without changing anyone's role.

RoleHierarchy levelDefault action grantsTypical scope
AdministratorLevel 0Implicit — holds every permissionOversight, user management, system settings
Program HeadLevel 1exams.create, exams.update, exams.approve, behavior.resolve, reports.export, sessions.gradeReviews and approves submitted exams before they can publish
Guidance StaffOperationalexams.create, exams.update, behavior.resolve, reports.export, sessions.gradeDay-to-day exam authoring and monitoring
Teacher / Exam CreatorOperationalSame as Guidance StaffCreates and submits exams for their own courses
ProctorOperationalNone by default (module access only)Live monitoring and behavior review; no mutating grants until delegated
Examinee—NoneTakes assigned exams, views own results

Full registry in backend/core/security/modules.py (module visibility) and backend/core/security/permissions_registry.py (action grants).

Exam approval chain

Directly answers Area 01's "Administrator responsibilities" item: stop making the administrator responsible for creating every exam. Teachers, Guidance Staff, and Program Heads create and submit exams; a Program Head (or Admin) reviews, approves, or rejects them. Only an approved exam may be published by a non-admin creator — an admin retains the same bypass it holds everywhere else in the system, so this adds a review gate without introducing a second point of failure.

1. Draft

Creator builds the exam. approval_status = not_submitted.

2. Submit

Creator submits once publish-readiness passes (≥1 question, valid answer keys). approval_status = pending; logged to exams_approval_event.

3. Review

Program Head/Admin approves or rejects (with a note). Rejection returns the exam to the creator, who can revise and resubmit.

4. Publish

approval_status = approved unlocks POST /api/exams/{id}/publish/ for the creator; exam status moves draft → active.

Registration & OTP verification

Answers Area 01's "Registration & verification" item. Registration collects only essential fields — the profile photo is optional at signup and can be added later from the profile page, rather than blocking account creation. Password confirmation is required. Immediately after account creation, a 6-digit OTP is emailed; the code is stored hashed (never in plaintext), expires after 10 minutes, allows 5 incorrect attempts before requiring a resend, and is rate-limited to one send per 60 seconds. A "Verify your email" banner in the signed-in workspace (dismissible per session, not a hard gate) makes the pending step visually clear without blocking use of the app.

Technologies, Concepts, and Theories

The platform follows a classical computer-vision pipeline—data collection → preprocessing → feature extraction → classification/scoring—embedded in a full-stack web architecture. Technologies are grouped by layer; each entry notes where it is applied in Knowing Eye.

Frontend

React 18 + Vite 6

Single-page application shell. Powers the exam-taking flow (exam-taking-backend.tsx), live monitoring dashboard (monitoring.tsx, session-monitor.tsx), exam builder, and admin reports.

TypeScript

Static typing across frontend/src/. Enforces API contracts in core/config/api.ts and feature modules (auth, exams, monitoring, reports).

React Router 7

Client-side routing with role-gated pages via protected-route.tsx—admin routes (exam builder, monitoring) vs. examinee routes (dashboard, exam session).

TanStack React Query

Server-state caching for reports and session lists (features/reports/hooks/), reducing redundant REST calls on the dashboard.

Tailwind CSS 4 + Radix UI (shadcn/ui)

Design system in shared/components/ui/—forms, dialogs, tables, and charts used across login, exam setup, and monitoring views.

Browser Media APIs

getUserMedia(), Canvas JPEG encoding, and WebSocket in shared/hooks/use-monitoring.ts capture and stream ~1 FPS webcam frames during an exam session.

Backend

Django 6 + DRF

Feature-based modular monolith under backend/features/—authentication, exams, session lifecycle, monitoring REST fallback, behavior logs, and PDF reports.

Django Channels + Daphne (ASGI)

Real-time WebSocket consumers at /ws/monitoring/{session_id}/ receive frames, invoke the AI adapter, and broadcast alerts to admin observers.

PostgreSQL / SQLite

Relational persistence via Django ORM. SQLite in local development; PostgreSQL 15+ in production for users, exams, sessions, behavior logs, and identity embeddings.

Redis + channels-redis

Production channel layer for multi-worker WebSocket broadcast—keeps live alert notifications synchronized when Daphne is scaled horizontally.

ReportLab

Generates downloadable PDF exam and session reports from features/reports/views.py.

AI / Computer Vision

Production pipeline: backend/ai/knowing_eye/, integrated through backend/ai/adapter.py. Pre-trained benchmark accuracies below are from published model evaluations; project-specific UAT metrics are tracked in Part D.

MediaPipe Face & Pose

In project: face_detector.py and pose_detector.py extract 468 face landmarks, head yaw/pitch, and body keypoints for gaze and posture scoring.
Accuracy: Face detection ~98% precision on frontal faces; pose landmark PCK@0.2 ~95% on visible joints (Google benchmarks).

ArcFace / InsightFace (buffalo_l)

In project: arcface_backend.py produces 512-D embeddings; enrolled at exam start and verified each frame via cosine distance (identity_match_threshold: 0.42 in pipeline.yaml).
Accuracy: LFW 99.77%, CFP-FP 98.56%, AgeDB-30 98.18% (InsightFace model zoo).

OpenCV + NumPy

In project: preprocessing/frame.py handles BGR conversion, resize (≤640 px), denoise, and YCbCr histogram equalization before inference.

Threshold-based behavior classifier

In project: behavior/scoring.py and behavior/temporal.py map detections to 0–100% compliance metrics, rule-based event flags, and sliding-window suspicious-pattern alerts.

Deployment / Server

Nginx

Reverse proxy in production—TLS termination, SPA static hosting (frontend/dist), REST proxy to /api/, and WebSocket upgrade on /ws/.

Serves the Django ASGI application (core/config/asgi.py) on port 8000; managed via systemd in production (docs/deployment.md).

Security

PBKDF2 password hashing

Django's default hasher stores credentials in authentication_user.password—never in plaintext.

JWT (SimpleJWT, HS256)

Access + refresh tokens issued at /api/auth/token/; auto-refreshed by frontend/src/core/config/api.ts. WebSocket auth via query-string token in JWTAuthMiddleware.

RBAC + PBAC

Three-tier role + module + action model (see Access Control) enforced on REST endpoints and UI routes—draft exams, approvals, and admin dashboards are gated per role, not just admin-vs-everyone-else.

OTP email verification

6-digit code hashed and stored in authentication_email_verification, emailed on registration and re-sendable from the workspace; 10-minute expiry, 5 attempts, 60s resend cooldown.

TLS, HSTS & secure cookies

Production settings (settings/production.py) enable SECURE_SSL_REDIRECT, HSTS, HttpOnly/Secure cookies, and X-Frame-Options: DENY when DEBUG=False.

CORS whitelist

CORS_ALLOWED_ORIGINS restricts API access to the deployed SPA origin; credentials are allowed only from trusted domains.

UI Readability & Contrast Audit

Directive Area 02 ("Readability & contrast"): the panel cited poor contrast, an overly dark default theme, and "eliminate gray-on-gray combinations." Two root causes were found and fixed, and every design-token pair was measured against WCAG 2.1 (4.5:1 for body text, 3:1 for large text and UI-component boundaries like input borders) rather than adjusted by eye.

Root cause 1 — the app defaulted to dark for every first-time visitor

core/providers/theme-provider.tsx set defaultTheme="system", and the toggle button in shared/components/common/theme-toggle.tsx independently manipulated <html>'s class list with its own useState("dark") default — bypassing the theme provider entirely and defaulting anyone without a saved preference to dark, regardless of system preference. Fixed: the toggle now reads/writes theme exclusively through next-themes' useTheme(), and the provider defaults to light.

Root cause 2 — input and button borders were measured, not eyeballed, and found near-invisible

Body text (--foreground/--background, --muted-foreground/--muted) already passed at 4.7–15:1 in both themes and was left unchanged. Decorative-only borders (card outlines, table dividers, section rules) were deliberately not pushed to the 3:1 UI-component threshold — WCAG 1.4.11 scopes that requirement to boundaries needed to identify a component, and these carry redundant cues (shadow, background shift); forcing every card outline to 3:1 would have been a much larger, unrequested visual change for no accessibility gain. All values computed via the WCAG relative-luminance formula against the actual rendered/composited color, not the raw token in isolation.

Every ratio above is asserted, not just written down: frontend/src/styles/theme-contrast.test.ts reimplements the WCAG relative-luminance formula and fails the build if a future token edit regresses a pair below its threshold. Disabled controls (.icon-btn:disabled's 0.45 opacity, the shared Button/Input disabled:opacity-50 utility) are deliberately excluded from that test rather than silently ignored — WCAG 2.1 SC 1.4.3 and 1.4.11 both exempt inactive UI components from contrast requirements, so opacity-dimming is the correct treatment, not a gap.

Two things were required — real institutional marks in place of placeholder art, and a sweep to catch any component still wearing an unmodified component-library default.

Templated-component sweep

Directive Area 02 also asks for a sweep of "obviously templated / AI-generated-looking" components. Rather than eyeball 45 files in shared/components/ui/, the check was run as a grep for the tell: unmodified shadcn/ui defaults lean on Tailwind's stock gray-*/slate-*/zinc-*/neutral-*/stone-* palette instead of this app's design tokens.

grep -rE '\b(bg|text|border|ring|from|to|via)-(gray|slate|zinc|neutral|stone)-[0-9]+' frontend/src
→ no matches

Zero hits across the entire frontend, not just ui/. Every surface — buttons, inputs, badges, cards, switches, tables, sidebars, dialogs — resolves color through the token layer in styles/theme.css, so the sweep is complete rather than partially spot-checked.

CV Pipeline Stages

1. Data Collection

Browser getUserMedia() captures webcam video; canvas encodes JPEG/base64 at ~1 FPS. Transport: WebSocket /ws/monitoring/{session_id}/ (REST /api/monitoring/frame/ fallback).

2. Pre-processing

Base64 → BGR; resize to ≤640px; optional denoise; YCbCr histogram equalization. Config: backend/ai/config/pipeline.yaml.

3. Feature Extraction

MediaPipe (468 face landmarks, head yaw/pitch, posture ratios) and ArcFace identity embedding.

4. Classification & Scoring

Threshold-based 0–100% metrics, rule-based event flags, sliding-window temporal patterns, and weighted aggregation into overall_compliance_pct.
