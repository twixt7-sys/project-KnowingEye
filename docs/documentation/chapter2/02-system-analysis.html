Functional and Non-Functional Requirements

Requirements were derived from capstone objectives, stakeholder input from IT faculty, and iterative prototype validation. Each item is numbered for traceability to test cases (prefixes FR-, NFR-).

Functional Requirements

  1. The system shall allow users to register and authenticate using username/password with JWT access and refresh tokens.
  2. The system shall enforce role-based access control with two roles: Administrator and Examinee.
  3. Administrators shall create, update, publish, archive, and delete exams and associated questions.
  4. Administrators shall manage user accounts (activate, deactivate, assign roles).
  5. Examinees shall start an exam session for a published exam within its availability window and attempt limit.
  6. The system shall enforce one active session per examinee per exam at a time.
  7. Examinees shall answer questions within a timed session and submit responses for automatic scoring.
  8. The system shall calculate percentage score and pass/fail based on the exam passing threshold.
  9. Examinees shall enroll a reference face image before or during monitoring for identity verification.
  10. The system shall capture webcam frames and analyze behavior in near real time via WebSocket (REST fallback).
  11. The AI pipeline shall detect face absence, multiple faces, gaze deviation, poor posture, and identity mismatch.
  12. The system shall persist behavior events and generate severity-classified alerts linked to the session.
  13. Administrators shall view live alerts and resolve them through the behavior API.
  14. Administrators shall access dashboard KPIs, session reports, timeseries analytics, and CSV export.
  15. Examinees shall view their own session history and results where authorized.

Non-Functional Requirements

  1. Performance: Frame analysis target ≤ 300 ms per frame at ~1–5 FPS; REST API responses ≤ 2 s under normal load.
  2. Scalability: Support multiple concurrent examinees; production uses a Redis channel layer for multi-worker WebSocket broadcast.
  3. Security: Passwords hashed (Django PBKDF2); JWT for API/WS auth; HTTPS/WSS in production; RBAC on all endpoints.
  4. Reliability: AI adapter degrades to a deterministic stub when ML dependencies are unavailable; monitoring API contract is always honored.
  5. Usability: Responsive web UI; role-specific navigation; clear exam timer and compliance feedback during monitoring.
  6. Maintainability: Feature-based modular monolith; documented REST catalog; 37 automated backend tests.
  7. Portability: Runs on Windows/Linux; SQLite for development; PostgreSQL for production without code changes.
  8. Privacy: Raw video frames are not stored by default (KE_STORE_FRAMES=False); only derived metrics and events persist.

LMS Benchmarking

Directive Area 03 ("LMS benchmarking", P0): "don't reinvent the LMS examination workflow - benchmark it" against Google Forms, Jotform, and a comparable LMS quiz engine before finalizing the exam-creation workflow. This section is placed before the design artifacts below it (rather than written up after the fact) because the Directive's design decisions in this chapter cite it directly. Google Forms and Jotform are general-purpose form builders occasionally used for quizzes; Moodle's Quiz activity is used as the "comparable LMS" column because it is the most widely deployed open-source exam-specific quiz engine and the closest architectural peer to an admissions-testing platform.

CapabilityGoogle FormsJotformMoodle QuizKnowing Eye
Question creation flow Inline single-page builder; each question is a card with an inline type picker. Drag-and-drop palette of form-field widgets onto a canvas. Questions authored independently in the Question Bank, then added to a quiz. Inline "Add question" dialog on the exam builder, typed to one of 4 question types - closer to Forms' inline model, but exam-scoped rather than a global bank.
Drag-and-drop reordering Yes - drag any question card to reorder. Yes - full builder is drag-and-drop. Yes - drag handle on the quiz's "Edit quiz" page. Yes (sortable-question-list.tsx, server-persisted via questions/reorder) - locked once published or while a session is in progress, matching how Moodle locks a quiz with existing attempts.
Question types supported 10: short/paragraph text, multiple choice, checkboxes, dropdown, linear scale, grids, date, time, file upload. General-purpose form fields (text, choice, matrix/Likert, ranking, signature, payment, file upload) - not exam-specific. 12+: multiple choice, true/false, short answer, matching, numerical, essay, calculated, drag-and-drop, cloze, and more. 4, deliberately: multiple choice, true/false, short answer, essay. Justification: Guidance's psychological/behavioral content (Directive "Guidance-specific scope") doesn't need Moodle's calculated or cloze types - matching that breadth would add builder complexity with no assessment value here.
Randomization / shuffling Shuffle question order (global toggle) and shuffle answer order per multiple-choice question; no true per-student random draw from a bank without an external Sheets workaround. No native shuffling - a submission tool, not a quiz engine; branching uses conditional logic, not randomization. Shuffle within quiz, shuffle answer choices, and a "Random question" slot type that draws N questions from a question-bank category per attempt. shuffle_questions + shuffle_options (with a per-question override) plus QuestionPool random-draw-N-of-M - matches Moodle's random-bank-draw capability, going beyond Google Forms' simple reorder-only shuffle.
Search & filtering None in Forms itself - relies on Google Drive's file search. Dashboard-level search/filter/sort by folder across forms, not within one form's questions. Question Bank has a category tree plus search and filter by type/tag - the strongest comparator. DRF SearchFilter + OrderingFilter + filterset_fields (status, category, department, approval_status) on the exam list endpoint, with an ExamCategory taxonomy - classification at the exam level rather than per-question, appropriate for Guidance's exam-level content types rather than a shared cross-exam item bank.
Scheduling / publishing Only an "Accepting responses" on/off toggle; no native open/close date-time window without Apps Script. A "Form Scheduler" widget sets an open/close date and a closed-form message. Native "Open the quiz" / "Close the quiz" date-time fields, enforced server-side. available_from/available_until enforced server-side (assert_exam_available_for_user, blocks session start outside the window), a derived Upcoming/Active/Closed/Expired state, plus the submit -> review -> approve chain from Area 01 gating publish itself - stricter than all three benchmarks, since Directive Area 01 explicitly rejected single-admin-controls-everything.
Question bank behavior None. None. Dedicated Question Bank app: questions are reusable and versioned across many quizzes. Questions belong to one exam, not a cross-exam bank. Justification: exam cloning (duplicate_exam, carries questions/sections/pools/attachments) plus in-exam QuestionPool draw covers reuse within an admissions cycle, which is what Guidance actually does; a shared cross-exam bank isn't cited anywhere in the Directive and would be scope the panel didn't ask for.
Results workflow Auto-grades objective questions instantly; manual review only via the per-response view; no release-scheduling or grading-hold gate. No auto-grading (not a quiz tool) - submissions land in Jotform Tables for manual review. Auto-grades objective types instantly; essay/short-answer needs manual grading; a teacher can manually toggle "don't show grades" until grading is done. Auto-grades objective types on submit; an essay or unmatched short-answer flags the session PENDING_REVIEW and the score fields are withheld from the examinee (not just the answer key) until every flagged response is graded, then the session auto-completes and emails the examinee - the hold is computed automatically rather than depending on a teacher remembering to toggle it, as Moodle requires.

Every Sprint 3 design choice that comes out narrower than a benchmark (question types, cross-exam question bank) is a deliberate scope decision cited above, not an oversight; every choice that comes out stricter (scheduling, results release) traces directly to an earlier Directive area (Area 01's approval chain, Area 03's own "hold essay results" instruction) rather than being invented here.
