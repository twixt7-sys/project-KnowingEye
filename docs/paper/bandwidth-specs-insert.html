Bandwidth and Real-Time Data Requirements

Knowing Eye does not transmit continuous video. During a monitored examination, the examinee's browser captures still frames from the webcam, scales each frame to 480×360 pixels, encodes it as a JPEG image at quality 0.6, and sends it to the server as a binary WebSocket message. The target rate is five frames per second. The server analyzes each frame and replies with a short JSON result. The browser sends the next frame only after the reply to the previous one arrives, so the actual rate never exceeds what the server can process.

To determine the bandwidth and the volume of data processed in real time, 60 frames were captured from a laptop webcam at 640×480 pixels and encoded with the same settings the browser uses. Each frame was then passed through the production analysis pipeline, which consists of MediaPipe face and pose landmark detection and ArcFace identity verification. Message sizes were measured directly. Bandwidth figures were derived from the measured sizes and the configured frame rates.

Server Throughput Testing

Server throughput was measured by running one to sixteen simulated examinees against a single server process on an Intel Core i5-11300H laptop (4 cores, 8 threads, 7.7 GB RAM). Each simulated examinee sent the next frame only after receiving the reply to the previous one, in the same way as the browser. The frames contained a face, so both MediaPipe detection and ArcFace identity verification ran during the test.

Measured on an Intel Core i5-11300H (4 cores, 8 threads) with 7.7 GB RAM. Ranges show the spread across repeated runs.

Server processing is the limiting factor. Each analyzed frame consumed about 0.85 CPU-core-seconds, of which ArcFace identity verification accounted for roughly 85 to 90 percent. A single server process analyzed about 5.5 to 6.7 frames per second in total, regardless of how many examinees were connected, so each additional examinee reduced the frame rate of the others. Because the face and pose detectors are shared within a process and run one frame at a time, a process cannot exceed about 10 frames per second even on a larger machine. Supporting 30 examinees at five frames per second therefore requires about 150 frames per second of capacity, distributed across at least 15 server processes connected through a Redis message broker.

Because each browser waits for the server's reply before sending the next frame, the system degrades gradually rather than failing under load. An overloaded server analyzes frames less often, and the bandwidth used falls with it.

Message sizes do not depend on server hardware and are expected to hold in deployment, although brighter or more detailed scenes produce larger images. For this reason, capacity planning should use the 95th percentile sizes. Processing figures were measured on a development laptop that had less than 1 GB of free memory during testing, and repeated runs varied by up to a factor of two. These figures are therefore conservative. A dedicated server is expected to perform better, and the processing measurements should be repeated on the deployment hardware before final capacity is stated. Network overhead was estimated rather than captured.
